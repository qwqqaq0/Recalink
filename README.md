# Bookmark Recall

一个以“找回”为核心的轻量书签管理器。它不要求用户先建立完美的文件夹或标签体系，而是在收藏时保存可检索的网页内容，在需要时通过全文检索和有限的 AI 辅助，帮助用户找回“记得内容、但忘了标题和位置”的网页。

> 当前阶段：项目构想与可行性验证。本文档描述方向和第一版边界，不代表所有技术选型已经确定。

## 1. 背景

浏览器收藏夹通常保存标题、URL 和文件夹位置。随着收藏数量增加，会出现几个问题：

- 记得网页讲过什么，却不记得标题和网址；
- 文件夹只能表达一种归属，难以覆盖交叉主题；
- 收藏时建立的分类，未必符合未来寻找网页时的思路；
- 自动生成大量标签容易造成同义标签、粒度混乱和长期失控；
- 仅根据标题、URL 和简短描述搜索，无法利用网页正文中的具体概念。

本项目首先解决“找不到已经收藏的网页”，而不是试图一次性重做完整的知识管理系统。

## 2. 核心假设

如果在收藏网页时提取并保存主要正文，再对标题、URL、正文和少量结构化信息建立索引，那么用户使用记忆中的术语、问题描述或内容片段进行搜索时，找回效果应明显优于浏览器原生收藏夹。

AI 的作用是增强模糊查询，而不是取代全文检索，也不是为了给每个网页生成尽可能多的标签。

## 3. 产品定位

Bookmark Recall 是一个面向个人用户、优先支持 Edge/Chromium 的轻量书签管理器，特点是：

- 找回优先，而不是归档优先；
- 正文可检索，而不是只搜索标题和 URL；
- 普通搜索是可靠底座，AI 是可选增强；
- 优先兼容用户现有的浏览器收藏；
- 第一阶段面向单用户和个人部署；
- 搜索结果说明匹配原因，避免不可解释的“语义相似”。

它不是完整复刻 Raindrop、Linkwarden 或 Karakeep，也暂不以多人协作、网页永久归档或阅读器体验为重点。

## 4. 第一版目标

第一版只完成一条可验证的闭环：

1. 导入 Edge/Chromium 收藏夹，保留原有文件夹信息；
2. 通过浏览器扩展收藏当前网页；
3. 从已经渲染的页面中提取标题、URL、元数据和主要正文；
4. 将书签及清洗后的正文发送到后端；
5. 后端异步处理内容并建立全文索引；
6. 用户通过关键词或自然语言搜索自己的书签；
7. 系统返回排序后的结果、命中片段和匹配原因；
8. 用户可以打开、编辑或删除书签。

## 5. 第一版不做什么

为控制项目规模，第一版明确不包含：

- 多用户和团队协作；
- 移动端客户端；
- 浏览器之间的完整双向同步；
- PDF、截图、SingleFile 等完整网页归档；
- 复杂的父子标签和知识图谱；
- 自动重构整个标签体系；
- AI 自动创建大量标签；
- 网页问答、聊天和通用个人知识库；
- 推荐系统和“稍后阅读”提醒；
- 对所有登录页面、动态应用和特殊站点保证正文提取成功。

## 6. 内容采集

### 6.1 为什么优先由浏览器扩展提取

纯后端爬取容易遇到登录状态、JavaScript 动态渲染、反爬和服务端看到的页面与用户实际页面不同等问题。第一版优先由扩展读取用户当前已经渲染的页面，再进行正文提取。

后端抓取可作为公开网页的补充和重试手段，但不是唯一入口。

### 6.2 建议保存的数据

- 页面标题；
- 原始 URL 和规范化 URL；
- 域名；
- meta description；
- 页面语言；
- 主要标题和小标题；
- 清洗后的正文文本；
- 收藏时间和最后处理时间；
- 原浏览器文件夹；
- 用户备注；
- 用户手动标签；
- 内容提取状态和失败原因。

默认不执行页面脚本，不保存密码、表单内容和隐藏输入。对于可能包含隐私信息的页面，需要在产品交互中明确提示正文会被发送到后端。

## 7. 搜索设计

### 7.1 基础搜索

基础搜索应在不调用模型时完整可用，至少覆盖：

- 标题精确匹配；
- URL 和域名匹配；
- 正文全文检索；
- 标签和文件夹过滤；
- 收藏时间过滤；
- 中英文关键词搜索。

初始排序可以综合标题命中、正文命中、词频、短语完整度、收藏时间和用户固定状态。

### 7.2 AI 增强

AI 仅在查询明显模糊或用户主动启用时参与：

- 将自然语言问题改写为可检索的关键词和相关术语；
- 补充同义词、缩写及中英文技术词；
- 对全文检索召回的有限候选进行重排；
- 在结果中生成简短、可核对的匹配说明。

例如用户输入：

> 之前那个讲数据库明明有索引却没有使用的文章

系统可以扩展出：

```text
数据库 索引未命中 query planner sequential scan EXPLAIN ANALYZE
```

模型不直接在全部书签中“凭感觉”选择答案，而是增强查询或重排已经由搜索引擎召回的结果。

### 7.3 可解释结果

每个结果至少展示：

- 标题和域名；
- 命中的正文片段；
- 命中了哪些词或概念；
- 主要排序原因；
- 是否经过 AI 重排。

用户应该能快速判断结果为什么出现，也能发现错误扩展或错误排序。

## 8. 标签定位

标签不是第一版的主要找回机制，只作为稳定主题的辅助筛选手段。

第一版建议：

- 支持用户手动创建和编辑标签；
- AI 优先从已有标签中推荐少量候选；
- 允许没有合适标签；
- AI 推荐的新标签必须由用户确认；
- 不把内容类型、处理状态、优先级和主题全部混入同一个标签集合。

精细概念由正文搜索负责，标签只保留具有复用价值的主题。

## 9. 概念架构

### 9.1 浏览器扩展

职责：

- 读取当前页面；
- 提取或提交可供后端提取的页面内容；
- 提供快速收藏入口；
- 在侧边栏或弹窗中进行搜索；
- 打开搜索结果；
- 显示采集状态和失败信息。

### 9.2 后端 API

职责：

- 书签的创建、读取、更新和删除；
- 导入浏览器收藏；
- 接收页面内容；
- 管理标签、文件夹和备注；
- 提供搜索接口；
- 管理可选的模型配置。

### 9.3 异步处理任务

职责：

- 清洗和规范化网页正文；
- 去重及 URL 规范化；
- 提取结构化字段；
- 更新全文索引；
- 生成可选的摘要、关键词或向量；
- 记录失败原因并支持重试。

### 9.4 搜索引擎

职责：

- 关键词和全文召回；
- 字段权重与过滤；
- 命中片段生成；
- 可选的向量召回；
- 混合排序和可解释信息输出。

第一阶段应优先选择部署简单、支持中文并能返回高亮片段的方案。具体使用 PostgreSQL 全文检索、Meilisearch、Typesense 或其他引擎，需要通过中文和技术内容样本测试后决定。

## 10. 初步数据对象

### Bookmark

- `id`
- `url`
- `normalized_url`
- `title`
- `domain`
- `description`
- `folder_id`
- `note`
- `created_at`
- `updated_at`
- `capture_status`

### PageContent

- `bookmark_id`
- `language`
- `headings`
- `plain_text`
- `content_hash`
- `extracted_at`
- `extractor_version`
- `failure_reason`

### Tag

- `id`
- `name`
- `normalized_name`
- `created_by`，区分用户创建与 AI 建议

### SearchFeedback

- `query`
- `bookmark_id`
- `position`
- `action`，例如打开、忽略或固定
- `created_at`

`SearchFeedback` 第一版可以只记录最少信息，用于离线评估排序，不急于实现在线学习。

## 11. 核心验证

在开发完整产品前，先验证“保存正文是否真的提高找回效果”。

### 11.1 测试数据

- 从真实 Edge 收藏夹中选择至少 200—500 个书签；
- 尽量覆盖技术文章、文档、教程、工具主页和普通网页；
- 记录正文提取成功率和失败类型。

### 11.2 查询集

人工编写至少 20—30 个接近真实记忆方式的查询，例如：

- 只记得文章讨论的问题；
- 只记得正文中的术语；
- 中英文混合表达；
- 记错标题但记得大意；
- 同主题下需要区分多篇相似文章。

每个查询预先指定期望找到的书签，避免测试时主观挑选结果。

### 11.3 对照实验

比较以下基线：

1. Edge 原生标题和 URL 搜索；
2. 标题、URL 与正文全文搜索；
3. 全文搜索加 AI 查询扩展；
4. 全文搜索加 AI 重排。

重点观察：

- 目标书签是否出现在前 1、前 5 和前 10；
- 正文提取成功率；
- 搜索响应时间；
- AI 是否带来稳定增益；
- AI 产生错误扩展的比例。

如果正文全文搜索没有明显优于 Edge 基线，项目应暂停或重新定位。如果全文搜索有效但 AI 没有稳定增益，则保留普通搜索，暂缓 AI 功能。

## 12. 主要风险

### 正文提取覆盖率

文章型页面通常适合 Readability 类算法，但工具主页、论坛、视频、动态应用和登录页面可能失败。系统必须允许正文缺失，并退化为标题、URL 和元数据搜索。

### 中文全文检索

不同搜索引擎的中文分词、技术词、英文缩写和代码符号处理效果差异较大，需要用真实收藏测试，不能仅根据功能列表选型。

### 隐私与安全

浏览器扩展可能读取登录后的网页内容。默认范围、用户提示、传输加密、内容删除和模型调用边界必须清楚，不能静默将私人页面发送给第三方模型。

### 内容版权与存储

第一阶段只用于个人检索，不公开重新分发保存的正文。后续如果增加公开分享或团队功能，需要单独评估内容授权和存储策略。

### AI 增益不足

模糊查询可能仅靠全文检索和同义词词典就能解决。必须通过对照实验验证模型调用的实际收益，不能把“使用了 AI”当成成功标准。

## 13. 建议里程碑

### M0：可行性实验

- 导入一批真实收藏；
- 批量提取公开网页正文；
- 建立最小全文索引；
- 完成基线查询测试；
- 输出是否继续项目的结论。

### M1：最小后端

- 书签 CRUD；
- 内容处理任务；
- 全文搜索和高亮片段；
- 导入与导出；
- 基础错误处理。

### M2：浏览器扩展

- 一键收藏当前页面；
- 浏览器侧正文提取；
- 快速搜索；
- 查看处理状态。

### M3：受控 AI 增强

- 查询扩展；
- 候选结果重排；
- AI 开关和模型配置；
- 与无 AI 基线进行效果比较。

### M4：有限标签辅助

- 手动标签；
- 已有标签推荐；
- 用户确认后创建新标签；
- 标签建议接受率评估。

## 14. 当前待决定事项

- 第一版是否只支持本地部署；
- 后端语言和框架；
- 搜索引擎选型；
- 扩展直接上传清洗文本，还是上传经过裁剪的 DOM；
- 登录页面的默认采集策略；
- 是否从一开始支持向量检索；
- MVP 是否提供独立 Web 管理界面；
- 项目的正式名称。

这些事项不应在完成 M0 验证前全部确定。当前优先任务是证明核心假设，而不是提前构建完整产品。
