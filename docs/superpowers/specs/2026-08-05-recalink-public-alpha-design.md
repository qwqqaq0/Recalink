# Recalink 公开 Alpha 整理设计

## 背景

当前项目以 `bookmark-recall` 为工作名称，已经具备本地 Web 管理、Edge/Chromium 扩展、书签同步、正文提取、全文检索以及可选 AI 辅助能力。项目准备在后续由维护者发布到公开 GitHub 仓库，但在发布前需要完成品牌统一、文档治理、扩展公开化、已确认的收藏标题体验改进，以及 Git 提交身份的隐私处理。

本轮只把本地仓库整理为可供维护者审查的公开 Alpha。不会创建远程仓库、推送代码、发布 Release，或提交浏览器插件市场。

## 目标

- 将产品名称统一为 **Recalink**，表达 `recall + link` 的产品含义。
- 让首次接触项目的用户能够理解用途、部署方式、数据流向和当前限制。
- 让公开仓库具备基础许可证、贡献、安全、隐私和变更记录文件。
- 补齐“收藏前自定义书签标题”的已确认体验缺口。
- 收紧并解释浏览器扩展权限，提供可识别的 Recalink 图标。
- 建立适合公开仓库的持续集成检查。
- 将本地 Git 历史中的公开 QQ 邮箱替换为 GitHub noreply 地址，并保留可恢复备份。
- 完整验证后把本地仓库交给维护者审查。

## 非目标

- 不实现用户登录、多用户、云托管或移动端。
- 不新增向量检索、网页问答或其他 AI 功能。
- 不制作插件市场宣传图、商店详情页或正式发布包。
- 不创建 GitHub 仓库、远程地址、版本标签或 Release。
- 不推送任何分支，也不读取或导入用户真实 Edge 收藏。
- 不因为 GitHub 公开而移除根包的 `private: true`；该字段用于防止 monorepo 被误发布到 npm。

## 项目身份与命名

- 产品展示名统一为 `Recalink`。
- 未来 GitHub 仓库建议使用 `recalink`。
- npm workspace 内部包、页面标题、扩展清单、Docker 描述、日志和用户文档中的旧品牌统一替换。
- 代码中的协议字段、数据库字段、环境变量和兼容性相关标识不为追求改名而无谓迁移；若标识只在项目内部使用且迁移风险低，则改为 `recalink` 命名。
- 本地工作目录名暂时保留 `bookmark-recall`，目录名不属于公开产品身份，避免为改目录产生额外路径和权限风险。
- 历史设计文档作为决策记录保留，但文档正文中仍处于未来时态的产品名称需要在不破坏语义的前提下更新为 Recalink。

## 收藏前自定义标题

该部分实现遵循已批准的《收藏前自定义书签标题设计》，并纳入公开 Alpha 验收：

1. 扩展 popup 打开时读取当前活动标签页标题；无标题时回退到 URL。
2. 标题显示在可编辑输入框中，用户可在收藏前修改。
3. 标题首尾空格被移除，上限为 500 个字符；空标题不能提交。
4. 最终标题同时用于 `browser.bookmarks.create()` 和上传到 Recalink 的采集载荷。
5. Readability 提取出的标题不得覆盖用户确认的标题。
6. 当前页面不是 HTTP(S) 或采集失败时，沿用现有错误与补偿策略。
7. 不修改后端接口和数据库结构，复用现有 `title` 字段。

实现采用测试先行：先覆盖标题默认值、URL 回退、规范化、长度限制、空值拒绝和采集载荷覆盖，再调整 popup。

## 扩展公开化

- 为 16、32、48、128 像素场景提供一致的 Recalink 图标；优先使用可追踪、易维护的仓库原生 SVG/生成脚本与导出的 PNG，不引入来源不明的素材。
- 检查 `bookmarks`、`storage`、`activeTab`、host permissions 等权限是否与代码匹配。
- 若 `scripting` 未被源码或构建产物使用，则移除；任何保留权限都在 `PRIVACY.md` 中解释用途。
- options 页面继续只把 API 地址和令牌保存在 `chrome.storage.local`。
- 只有用户显式点击收藏时才读取当前登录页面的可见正文。
- 生成可通过 Edge“加载解压缩扩展”使用的生产构建目录，但不提交构建产物，除非现有仓库策略明确要求提交。

## 持续集成

新增 GitHub Actions 工作流，在受支持的 Node.js 24 环境执行：

1. `npm ci`；
2. lint 与格式检查；
3. TypeScript 类型检查；
4. 单元和不依赖真实用户数据的集成测试；
5. Web、API、worker 和扩展生产构建。

CI 不使用真实 AI 密钥、不访问真实书签、不依赖维护者本机路径。需要外部服务的测试继续使用合成夹具或项目既有的测试服务配置。Docker 完整烟雾测试保留为本地发布前检查，除非它在当前 CI 环境中能够稳定、合理时长地运行。

## Git 身份隐私与历史重写

公开提交身份统一为：

```text
qwqqaq0 <174874143+qwqqaq0@users.noreply.github.com>
```

历史重写属于会改变 commit hash 的操作，按以下顺序执行：

1. 确认工作区干净，并记录当前分支与 HEAD。
2. 在仓库外的本机临时目录创建包含全部本地 refs 的 Git bundle；校验 bundle 可读取并记录位置。
3. 将仓库级 `user.name` 和 `user.email` 设置为上述公开身份。
4. 仅把匹配旧私人邮箱的作者和提交者邮箱改为 noreply；旧地址在本地执行时读取，不写入公开文件；保留姓名、时间、提交信息、树内容和其他贡献者身份。
5. 清理仅用于重写的临时 refs，避免未来误推送仍含旧邮箱的引用；bundle 作为本地恢复介质保留到维护者完成审查。
6. 扫描所有可达提交，确认 QQ 邮箱不再出现。
7. 输出重写前后 HEAD 和提交映射摘要，明确告知维护者 commit hash 已变化。

设计文档与公开化代码先以正常提交完成，历史重写放在所有内容、测试和审查准备完成之后执行，从而只进行一次重写。不会自动 force push，因为仓库当前没有远程地址，发布也不在本轮范围内。

## 测试与验收

### 自动验证

- 收藏标题纯函数和 popup 交互相关测试通过。
- `npm run verify` 通过。
- 所有工作区生产构建通过。
- 扩展生产构建成功，manifest 权限与设计一致。
- Docker Compose 烟雾测试通过，包括合成书签导入、正文唯一术语搜索和 AI 故障降级。
- GitHub Actions 配置可被本地静态检查，命令与本地验证命令一致。

### 公开性检查

- 已跟踪文件和完整可达 Git 历史中不包含 QQ 邮箱、真实 API 密钥、扩展令牌或用户收藏数据。
- 文档不包含个人绝对路径、无法访问的内部链接或虚假的完成声明。
- 旧产品名只在必要的历史说明、兼容标识或目录路径中出现。
- MIT、隐私、安全、贡献和变更记录文件相互一致。
- 扩展权限均有源码依据和文档说明。
- `git status` 干净，没有远程地址，没有推送或发布行为。

### 人工验收

- 在合成页面上修改标题后收藏，Edge 收藏名称与 Recalink 详情标题一致。
- 按 README 从干净配置启动项目并加载扩展，主要路径可理解且可执行。
- 维护者收到变更摘要、测试结果、bundle 位置、历史重写说明和未来发布建议。

## 风险与控制

- **重写历史不可逆感强**：通过重写前 bundle、可读性校验和一次性重写降低风险。
- **全局改名遗漏或误改协议**：先搜索分类，再按展示身份、内部包名和兼容标识分别处理；用测试和构建验证。
- **公开文档夸大能力**：README 只描述实际验证通过的功能，并显式标记 Alpha 与限制。
- **扩展权限误删**：以源码搜索和扩展流程测试为依据，不凭 manifest 表面判断。
- **CI 与本地环境不一致**：CI 复用根脚本，禁止依赖个人路径和真实凭据。
- **图标扩大设计范围**：只做清晰、可辨认的基础标识，不展开完整品牌系统或商店素材设计。

## 交付状态
